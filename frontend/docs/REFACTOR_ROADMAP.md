# 智慧医疗管理系统重构路线

本次重构不再以旧系统的 53 个模型和 10 类角色为产品边界。旧 Django 应用仅作为字段与历史数据参考，新系统围绕管理员、医师、患者三类身份和一条核心诊疗链路重新建设。

## 架构决策

- 新前端只调用 `/api/v1/`，认证采用 JWT Bearer Token。
- 患者是可登录账户；患者只能访问自己的医疗数据。
- 医师的数据范围由诊疗关系决定，不能任意浏览全部患者。
- 管理员管理账户和业务配置，但不能覆盖医师已确认的临床结论。
- 护理、住院床位、救护车、完整收费、保险、库存和 HR 不进入第一版主流程。
- 智慧服务只保留真实接口和任务状态，不展示伪造的 AI 诊断结果。

## 阶段一：新项目骨架（已完成）

- 三角色路由和动态导航。
- 登录、患者注册、个人中心入口。
- 管理员、医师、患者工作台框架。
- `/api/v1/` 请求层和路由权限守卫。
- 核心模块页面骨架，移除旧通用工作区与护理端入口。

后端已建立独立 `smartmedical` 项目、`smartmedical.sqlite3`、`/api/v1/`、JWT 登录、患者注册和三角色自定义用户；旧系统通过 `legacy_manage.py` 保留。

## 阶段二：基础资料与预约（已完成）

- 科室、医师档案、患者档案。
- 医师排班和离散预约号源。
- 患者按科室、医师、日期选择号源。
- 预约状态机：待就诊、就诊中、已完成、已取消、爽约。
- 号源唯一约束与事务锁，防止重复预约。

验收流程：管理员创建医师和排班，患者注册后成功预约，医师能够看到本人预约。

## 阶段三：诊疗闭环（已完成）

- 医师统一接诊工作区。
- 电子病历草稿、确认和补充更正记录。
- 处方主表与药品明细。
- 检查申请、检查报告和受控文件下载。
- 患者查看本人已确认病历、处方和已发布报告。

验收流程：患者预约 → 医师接诊 → 病历确认 → 开具处方和检查 → 报告发布 → 患者查询。

## 阶段四：统计、安全与质量（已完成基础版）

- 三类角色工作台真实统计。
- 关键写操作和敏感读取审计。
- 文件格式、大小、归属和下载权限校验。
- API 分页、筛选、排序和统一错误格式。
- 权限隔离、状态转换、重复挂号及文件访问测试。

## 阶段五：智慧医疗扩展（接口预留已完成）

- 智能服务目录、分析任务、任务结果数据模型。
- 医学文件与 AI 任务关联。
- 通过服务类型和端点字段预留本地推理或远程 FastAPI 适配能力。
- AI 结果始终标记为辅助信息，并保留医师审核字段。

## 旧系统处理原则

旧应用暂时保留但不挂载到新前端。新核心流程稳定并完成数据迁移脚本后，再按依赖顺序停用旧 URL、模板和应用；不直接删除旧迁移或强行修改旧数据库。

## 当前验收证据

- `python manage.py check`：通过。
- `python manage.py makemigrations --check --dry-run`：无缺失迁移。
- `python manage.py test healthcare`：11 项核心 API 与权限测试通过。
- `npm run build`：Vue TypeScript 生产构建通过。
- 实际 HTTP：JWT 登录接口与 `/app/login` 页面返回 200，静态资源完整加载。
