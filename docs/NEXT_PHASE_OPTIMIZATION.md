# 系统业务闭环与演示数据实施记录

## 1. 阶段目标

下一阶段不继续堆叠独立页面，而是以“一个入口能完成一条真实业务链”为验收标准，系统性打通 Vue 页面、REST API、权限校验、状态流转、数据落库和审计记录。

本阶段的核心目标是：

1. 完成管理员、医师、患者三类角色的核心操作闭环。
2. 为关键业务建立明确且可验证的状态机，避免页面有按钮但后端不允许、后端有接口但前端无入口。
3. 将对象级权限、错误提示、事务和审计纳入每条业务链，而不只验证普通 CRUD。
4. 建立角色级 API 回归测试，后续重构时能够及时发现链路断裂。

## 2. 分阶段方案

### 阶段 A：前后端链路盘点与接口契约

- 建立“菜单/页面 → 前端服务 → API → Serializer/ViewSet → 数据模型”的链路清单。
- 为每个接口标注允许角色、对象范围、前置状态、成功后的状态和审计动作。
- 统一分页、字段校验和错误响应，前端展示具体字段错误。
- 清理仅有展示按钮但没有实际事件的入口，未完成能力明确标记为“规划中”。

验收结果：所有可点击的核心入口均有真实请求和可理解的成功/失败反馈。

### 阶段 B：核心诊疗闭环

- 管理员：创建医师 → 关联科室 → 配置排班与号源。
- 患者：查询科室/医师/号源 → 预约 → 取消 → 查询诊疗结果。
- 医师：接诊 → 创建并确认病历 → 开具处方/检查申请 → 录入并发布检查报告。
- 患者：查看已确认病历、处方、已发布检查报告及授权附件。

验收结果：使用三个角色账号可连续完成一条端到端演示流程，无需直接操作数据库或 Django Admin。

### 阶段 C：权限、状态和数据一致性

- 补齐预约、病历、处方、检查报告的合法状态转换。
- 所有患者医疗数据使用对象级查询范围隔离。
- 关键写操作使用事务，已确认/已发布的医疗内容禁止直接覆盖。
- 对敏感读取、创建、确认、发布、下载和账号管理记录审计日志。

验收结果：越权访问返回 403/404，非法状态转换返回 400，失败操作不产生半完成数据。

### 阶段 D：页面可用性与缺失模块

- 将当前通用资源页逐步替换为有业务动作的专用页面。
- 优先补齐医师患者列表/详情、患者预约入口、医师个人排班、审计日志筛选。
- 补齐药品目录管理、密码修改；费用模块根据毕业设计时间决定是否进入核心范围。
- 智慧服务在没有真实模型时只展示服务状态和接口契约，不生成模拟诊断结论。

验收结果：导航中的已启用菜单均可完成对应业务；非本阶段能力不会伪装成可用功能。

### 阶段 E：联调、测试与展示数据

- 后端为每条核心链路增加角色、对象范围、状态转换回归测试。
- 前端执行类型检查和生产构建，并补充关键页面的交互测试。
- 使用匿名化演示数据执行管理员、医师、患者三角色验收脚本。
- 输出接口清单、测试结果和答辩演示步骤。

验收结果：后端测试、前端构建和核心演示脚本全部通过。

## 3. 当前迭代（P0）

本次先修复两条阻断性链路：

1. 医师检查反馈：医师可以对本人申请的检查开始处理、录入/修改草稿、上传附件并发布报告；其他医师不可访问，患者只可查看已发布结果。
2. 管理员新增医师：创建账户、校验初始密码、关联有效科室、原子创建医师档案，并在响应和用户列表中返回医师编号与科室，前端展示准确的字段错误。
