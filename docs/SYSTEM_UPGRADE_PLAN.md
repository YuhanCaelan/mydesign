# 医疗系统升级优化计划

## 一、目标与范围

围绕“管理员能看清资源和就诊状态、医师能连续完成接诊、患者能看懂自己的检查与费用”升级现有 Vue + Django 系统。本计划覆盖账户、科室、门诊排班与就诊、患者检查费用、电子病历、床位六个模块。所有统计和明细均以现有业务记录为准，避免手工维护重复数据。

“病人－大夫简历关联”按以下业务含义落地：在门诊排班及就诊视图中，能从医师查看其简介、出诊安排和已预约患者，也能从患者查看对应医师及本次就诊记录。医师与患者的实际关联以预约记录为准，不建立永久的一对一关系。

## 二、现状与改造重点

| 模块 | 现状 | 改造重点 |
| --- | --- | --- |
| 用户账户 | 管理员单表混合显示医师、患者；创建时才区分角色 | 分为医师、患者两个选项卡，各自独立查询、分页和创建入口 |
| 科室 | 只有名称、介绍、启停 | 增加按日期查看的患者量、当前接诊、当班医师及详情入口 |
| 排班 | 主要显示医师时段和号源数量 | 增加“门诊就诊视图”，按日期/科室/医师展示患者与接诊状态 |
| 患者检查费用 | 费用列表有检查类别和发生日期，缺少时间统计 | 增加日期区间筛选、逐日/周期汇总及检查账单明细 |
| 电子病历 | 接诊页展示最近 10 条已确认病历；完整病历和历史检查需要跨页查找 | 建立患者纵向病历视图，在接诊页一站式查阅历史病历、检查报告和附件 |
| 床位 | 看板按科室、病区分组，已有占用详情 | 增加按房间优先的视图及选项卡，优化查床、筛选和占用查看 |

## 三、详细方案

### 1. 用户账户：医师与患者分栏

- 管理员“用户账户”增加“医师账户 / 患者账户”两个选项卡，切换时保留各自的关键字、状态、页码和每页条数。
- 医师栏展示医师编号、姓名、科室、职称、专业方向、联系方式及启用状态；患者栏展示患者编号、姓名、联系方式、建档时间及启用状态。点击行可进入对应档案。
- “新增医师”和“新增患者”使用各自表单，固定角色；保留禁用/启用及字段校验。管理员账号不混入业务账户列表。
- 后端 `users/` 增加 `role`、`is_active` 筛选，分页在服务端执行；列表返回患者编号及医师档案摘要。现有账号和档案不迁移角色，继续按原外键关联。
- 验收：两个栏目的总数、筛选和分页独立正确；新增账户只出现在对应栏目；禁用后不能登录，但历史记录仍可查。

### 2. 科室管理：资源与就诊可视化

- 科室卡片展示所选日期的预约总数、待就诊数、就诊中数、已完成数、当班医师数；历史患者按“该科室曾有有效预约的去重患者数”统计，并显示统计口径。
- 科室详情设“概览 / 当日就诊 / 医师与排班 / 历史患者”选项卡。当日就诊列出当前接诊患者、主诊医师、预约时间和状态；历史患者可按日期区间查询，点击进入患者或就诊详情。
- “当前就诊患者”定义为预约状态 `in_progress`，可能同时有多位；无人在诊时显示空状态。科室归属以**预约时的医师所属科室快照**为准，避免医师调科导致历史统计漂移；此项需为预约补充科室外键或名称快照，并对旧数据按既有医师科室回填。
- 管理员可看全院科室统计；医师只见其有诊疗职责的必要患者信息；患者端不展示科室患者清单。聚合接口负责统计，明细接口负责分页，不一次返回全量历史数据。
- 验收：同一日期的卡片数字与预约明细一致；多名患者同时就诊时完整显示；历史数据不因医师调科变化；无权限用户无法读取患者清单。

### 3. 门诊排班：患者－医师就诊关联

- 排班页保留“排班设置”，新增“门诊就诊”选项卡。按日期、科室、医师、状态筛选，采用“医师 → 排班时段 → 号源 → 患者”层级展示；空号源、已预约、就诊中、已完成状态颜色一致。
- 医师卡片可查看职称、专业方向和简介；预约行可查看患者档案摘要、本次主诉/预约原因、预约号和关联病历状态。管理员从此进入就诊详情；医师从本人预约进入接诊工作区。
- 同一患者多次预约分别展示，不因姓名相同合并；取消和爽约保留在历史视图。就诊状态直接读取预约状态，不另建一套门诊状态。
- 后端提供日期范围内的门诊关联列表或排班详情接口，采用分页、批量关联查询；复用已有排班、号源和预约模型。
- 验收：任选患者能追溯到对应医师、排班和号源；医师本人能一键进入接诊；取消、爽约与空号源显示准确；不同医师不能从此入口读取他人的病历草稿。

### 4. 患者检查费用：按日期与周期统计

- 患者“我的费用”增加“检查费用”视图，支持快捷周期（近 7 天、近 30 天、本月）和自定义起止日期；展示总额、已付、待付、每日趋势、按检查项目汇总及对应账单明细。
- 统计对象为患者本人、类别为 `examination` 且关联检查申请的账单；金额取账单金额/价格快照，不能用当前项目单价重算。已取消账单单独显示，不计入应付或已付合计；已付按账单状态计算。未形成账单的检查不计费。
- 日期口径统一使用账单 `charge_date`（费用发生日期），起止日均包含；页面注明该口径。后端校验日期格式、起止顺序及最大查询区间，返回汇总与可分页明细；空区间显示 0 和空图。
- 患者只能查本人费用；管理员可按患者查询；医师不通过此患者页面查看非本人负责的费用。统计查询和导出（若后续增加）都做对象级权限校验。
- 验收：日期边界、跨月、已取消、已支付/未支付与明细求和一致；其他患者 ID 不能越权查询；金额保留两位小数。

### 5. 电子病历：以接诊工作区为主入口的整体增强

- 接诊后，在诊疗工作区采用“本次病历 / 历次就诊 / 历次检查 / 处方与住院”分栏；患者身份、过敏史、既往病史固定可见。历史列表可按日期、科室、诊断、病历号筛选和分页，支持查看同一患者**全部**已确认病历及更正记录，而不是仅显示最近 10 条。
- 历次检查展示申请日期、项目、状态、结论、报告发布时间与授权附件；从检查可回到对应就诊和病历。从单条病历也能查看与其关联的检查、处方和住院记录。未发布报告仅按当前业务权限可见，不向患者提前展示。
- 当前病历继续采用“草稿 → 确认 → 完成诊疗”，确认后只能追加更正。优化录入：字段分组、必填提示、草稿保存反馈、确认前摘要核对、未保存离开提醒；诊断或既往内容可参考历史但不自动覆盖本次病历。
- 新建患者纵向病历接口，例如 `patients/{id}/clinical-history/`：按时间倒序分页返回已确认病历及相关检查摘要，详情按需加载；“本次病历”仍走现有预约工作区。权限以医师与患者存在有效诊疗关系为前提，且仅在诊疗需要的范围开放；管理员仅在业务授权场景读取，所有敏感读取记审计。
- 优先修正现有 `PatientViewSet` 对医师开放全部患者列表、检查列表对医师开放全院记录等宽泛读取范围，再开放纵向病历；医生可读取被授权患者的既往**已确认**病历，仍只能编辑自己本次接诊的草稿。患者只可查看本人已确认病历和已发布检查。
- 验收：接诊医生无需离开工作区，即可找到该患者任意一份历史已确认病历及检查报告；10 条以上历史记录仍可分页查全；未授权医师、其他患者无法读取；已确认病历不能被覆盖，更正有作者和时间。

### 6. 床位管理：房间优先视图

- “床位看板”增加“按房间 / 按科室”选项卡，默认按房间查看。将现有 `ward_name` 作为首期病区/房间分组字段，房间卡片展示总床数、空闲、占用、停用；点击房间展开床位卡及入住详情。保留科室、病区、占用与启停筛选。
- 管理员另有“床位配置”子页用于新增、编辑、启停及日费设置；占用床位仍禁止改号、改房间或停用。医生使用只读看板，通过占用床位进入住院详情。
- 首期不取消 `WardBed.department` 必填，也不直接修改住院记录和计费逻辑。如果后续明确要求床位完全脱离科室，则第二步引入独立房间实体与归属迁移，修改床位选择、唯一约束、入院校验和历史费用快照；完成数据迁移后再允许无科室床位。
- 验收：同一房间的床位及占用数一致；全院/筛选统计正确；新增或停用床位后看板刷新；占用床位不能被错误重新分配；窄屏可用。

## 四、实施顺序与交付

| 阶段 | 工作 | 预计工作量 | 交付检查 |
| --- | --- | --- | --- |
| 0. 口径和数据准备 | 确认日期、科室归属、门诊状态与医疗数据权限；补充预约科室快照和必要索引 | 2～3 人日 | 数据迁移可回滚，旧预约统计有归属 |
| 1. 基础管理 | 账户分栏、服务端筛选分页；科室概览与当日就诊 | 4～6 人日 | 管理员可按科室看到真实患者与在诊医师 |
| 2. 门诊视图 | 排班关联患者与医师简介、跳转接诊 | 3～5 人日 | 任一预约可从排班追踪到接诊 |
| 3. 临床重点 | 病历纵览接口、接诊页重构、历史检查联动与权限收紧 | 7～10 人日 | 医师完成“接诊→查既往→写病历→确认”流程 |
| 4. 患者与床位 | 检查费用周期统计；床位房间视图与配置页 | 5～7 人日 | 患者对账、管理员查床均可独立完成 |
| 5. 联调验收 | 角色权限、聚合口径、移动端、演示数据、端到端流程 | 3～5 人日 | 回归用例通过，演示链路可重复执行 |

合计约 24～36 人日，适用于一名前后端兼顾的开发者；并行开发可缩短日历时间。优先级：电子病历与权限、门诊关联、检查费用为 P0；账户与科室可视化为 P1；床位房间视图为 P1，完全取消床位科室归属为后续结构性改造。

## 五、数据、测试和上线要求

1. 示例环境允许清空并重建演示数据。先更新 `seed_smartmedical`，补齐多次就诊、跨科室、多人同时接诊、跨周期检查费用、多房间床位等样例，再执行重建并跑端到端演示；重建仅作用于示例环境。正式数据使用迁移和回填，不执行清空。
2. 关键接口测试覆盖管理员/医师/患者三类角色的对象级权限、分页、状态转换、日期边界、金额合计、科室归属及床位占用冲突。前端至少完成类型检查、生产构建和六个关键页面的人工操作验收。
3. 聚合统计以数据库查询或专用只读接口实现，列表分页返回；对 `Appointment` 日期/科室/状态、`MedicalRecord` 患者、`ExaminationOrder` 患者、`BillingRecord` 患者/类别/日期增加必要索引，并用示例数据检查查询量。
4. 发布前备份数据库和附件，先运行迁移与历史回填，再部署接口及前端；若统计口径与旧数据有差异，展示“历史数据按现有信息回填”的说明并校对样本。

## 六、最终验收场景

管理员创建医师和患者，在各自账户栏查询；进入科室查看当日在诊医师、患者与历史患者；从门诊排班找到某患者预约并进入诊疗详情。医师接诊后，在同一工作区查到该患者全部既往病历和已发布检查，完成本次病历确认。患者按自选日期区间查看检查费用趋势和明细。管理员按房间查看床位占用，进入在院患者住院详情。以上流程在重建后的示例数据上可重复执行，且越权读取被拒绝并留有审计记录。
